# RetrievalAttention: Accelerating Long-Context LLM Inference via Vector Retrieval

- 来源版本：[NeurIPS 2025 正式发表页](https://proceedings.neurips.cc/paper_files/paper/2025/hash/4e36d4049fb0fea195a8267c8dcd0824-Abstract-Conference.html)，DOI：`10.52202/085713-1816`

## 研究问题与核心思路

**RetrievalAttention 把固定前缀的 KV 存在 CPU 上，并为它们建立注意力感知向量索引。生成每个 token 时，系统按当前 query 检索重要 KV，在 CPU 上计算这部分注意力，再与 GPU 常驻部分的结果合并。前缀及其索引可以跨请求复用。**

### 为什么需要动态检索

长上下文 decode 既需要显存存放 KV，也需要带宽在每一步读取历史 KV。把 KV 卸载到 CPU 可以缓解显存不足，但如果每步仍要逐层取回全量 KV，PCIe 传输就会拖慢生成。

作者在图 2 的 128K 上下文样例中观察到，注意力权重集中在少数 token 上，而这些 token 的位置随生成步变化。只保留预先选定的重要 token，可能漏掉后续需要的信息。这项观察支持动态检索，但尚不足以保证所有模型和注意力头都有相同的稀疏度。

对固定 query，softmax 不改变分数排序，寻找高权重 key 因而可以转为最大内积检索。近似质量还取决于被丢弃的权重总量及其 value 内容：即使找准了 top-k，也可能丢失有用信息。

### 为什么不能直接套普通 ANNS

Q 和 K 来自不同投影，作者实测发现二者的分布明显偏离。按 K–K 相似关系建图或聚类后，从 Q 出发检索最大内积的 K 仍可能很费力。

在 Yi-9B-200K、Llama-3-8B-Instruct-262k 的 128,000-token 上下文上，普通 IVF 需要扫描较大比例的 key 才能达到较高的 top-100 召回率；HNSW 则在作者测试设置下容易陷入局部最优。作为对照，用 K 检索 K 时，同分布检索明显容易。附录中的 OOD 检索方法 RobustVamana 在这些注意力向量上也表现不佳。

我更看重这项工作的索引设计：用 Q 的检索需求组织 K。这里的依据是作者测得的分布差异；仅凭投影矩阵不同，还无法判断其他注意力模型会出现多大程度的索引退化。

### 固定前缀是使用前提

论文面向固定前缀占上下文大部分、且同一前缀会被多次使用的场景，例如对同一文档反复问答。前缀 KV 和索引提前离线准备，在线处理的是较短的新用户输入及后续生成。（§3、附录 F，PDF 第 5、21 页）

如果每个请求都换一份长文档，或长会话中不断修改历史内容，就要重新考虑构建成本。论文的在线 prefill/decode 延迟没有计入这部分离线工作。

## 实现路径

### 1. 离线：用 Q–K 关系构建注意力感知索引

固定上下文的索引构建过程如下：（§3.2、图 4，PDF 第 5–6 页）

1. 为固定上下文生成 KV，并用已有 Q 引导索引构建。这里的 query vector 指注意力向量，与用户的自然语言问题要区分开。
2. 为构建用 Q 查找精确 top-k K，建立 Q→K 近邻连接。构建时的 k 与在线默认检索预算 100 是两个参数。
3. 直接保存这张二部图，需要额外存储 Q，搜索时还要在 Q、K 之间绕行。作者借用 RoarGraph 的投影方法，连接共享 query 邻居的 key，再去掉索引中的 Q 节点。
4. 给投影后的 key 图补边，提高连通性。最终搜索在 key 图上进行，边的选择保留了 query 视角下的相关性。
5. 将动态检索所需的 KV 和索引存入 CPU 内存。GPU 常驻部分与动态检索集合分开，合并时每个 token 只计入一次。

投影同时改善了存储和搜索效率。表 5 中，Llama-3-8B 在相近 recall@100 下（不投影 0.951、投影 0.954），扫描比例从 13.2% 降到 1.7%。这组检索微实验没有单独列出上下文长度和测量批大小，也未给出对应的整模型加速幅度。（§4.4、表 5，PDF 第 9–10 页）

### 2. 在线 prefill：加载前缀 KV

请求到来后，系统逐层把固定前缀 KV 从 CPU 加载到 GPU，让新用户输入对完整前缀做 full attention。进入下一层时，释放上一层非静态部分的 GPU 副本，CPU 上的历史 KV 则保留。这样无需把所有层的长前缀同时放进显存。（§3.3、附录 B.2，PDF 第 6、20 页）

短用户输入的 KV 留在 GPU，与静态模式一起参与后续计算。因此，640 个静态 token 只是 GPU 常驻 KV 的一部分。

我的理解是，复用省掉了固定前缀内部的重复计算，新输入对前缀的注意力和相应 PCIe 传输仍然需要执行。附录 F 明确说明当前设计不优化 prefill；图 7 测量在线延迟时，前缀和索引已经准备好。

### 3. 在线 decode：在 CPU 计算检索部分的注意力

默认静态模式包含前 128 个 token 和最近窗口的 512 个 token，共 640 个；索引方法默认另检索 top-100 keys。GPU 用 FlashAttention 计算静态部分。CPU 收到当前 query 后遍历索引，取出对应 value，并在本地计算动态部分的注意力。（§4.1、附录 B.2，PDF 第 7、20 页）

每步主要跨 PCIe 传输 query、CPU 部分输出和合并所需的统计量；命中的 KV 留在 CPU 上计算。两端的部分计算可以并行，层间依赖、检索、同步和结果合并仍会影响每步耗时。

这里有几种不同的预算：640 是静态 token 数，100 是默认动态返回数，扫描量则是搜索过程中访问的候选数。作者所说的“扫描 1–3% key”指最后一项。完整 KV 仍需保存，实际参与注意力的 token 数还包括新用户输入等部分，并非每个请求都恰好是 740 个。

### 4. 合并两端的注意力结果

令 GPU 集合为 $W$，CPU 检索集合为 $\Omega$，二者不相交；选中集合 $I=W\cup\Omega$。对同一 query，记 $z_i=qk_i^T/\sqrt d$。两端分别计算局部 softmax 输出 $o_W,o_\Omega$，各自的归一化分母不同，合并时需要重新加权。（附录 B.1，式 3–5，PDF 第 19 页）

将论文的合并公式写成数值稳定形式：对 $S\in\{W,\Omega\}$，

$$
m_S=\max_{i\in S}z_i,\qquad
\ell_S=\sum_{i\in S}e^{z_i-m_S},\qquad
m=\max(m_W,m_\Omega).
$$

$$
\alpha_S=e^{m_S-m}\ell_S,\qquad
 o_I=\frac{\alpha_W o_W+\alpha_\Omega o_\Omega}
 {\alpha_W+\alpha_\Omega}.
$$

合并结果等价于在选中集合 I 上重新计算注意力。漏检和截断完整历史造成的误差仍然存在。

这里有两层近似：ANNS 可能漏掉真正的 top-k；即使找准了 top-k，集合外的累计注意力质量也可能不可忽略。Flat 消除了检索误差，计算的仍是稀疏注意力。

### GPU、CPU的KV分配策略

*Similarly to StreamingLLM [13], our current implementation uses fixed initial tokens and the last sliding window of the context as the static pattern and persists them in the GPU cache. All remaining tokens require index building for retrieval.*

常驻GPU的静态KV实际上是固定的初始token以及末尾的滑动窗口，**其余所有**token都要构建索引以供检索。prefill时仍需所有本层KV都进入GPU做一次Full attention。因此对于“单层全部KV缓存都无法全部放入显存”的场景，该策略的predill会失效，当然论文自己也提到没有优化prefill部分。

## 实验条件与关键结果

### 实验设置


- 主平台：单张 RTX4090，24GB 显存；Intel i9-10900X，10 个物理核；128GB DRAM。
- 主模型：Llama-3-8B-Instruct-262k、Yi-9B-200K、Yi-6B-200K。下文简称 Llama-3-8B、Yi-9B、Yi-6B，均指这些长上下文版本。
- RetrievalAttention、Flat、IVF 默认使用 640 静态 token 加 top-100 动态 key；所有层在 decode 使用稀疏注意力。部分任务另提高预算，见后文。
- StreamingLLM、SnapKV、InfLLM、Quest、InfiniGen 的保留或选择预算约为 2K，窗口、块和页配置见附录 A.1。MagicPIG 按上下文长度选择 LSH 参数，其预算与 top-100 检索不能直接等同。
- full attention 基线把 KV 卸载到 CPU，按层加载到 GPU。对照实验反映的是这一配置下的速度差异；全 KV 常驻 GPU 时需要另测。
- 论文未完整给出各项实验的权重/KV 精度、软件与库版本、采样设置及生成长度。表 9 未单独注明批大小，精度测试也未逐项列出输出长度和 batch，复现时还需要补齐这些条件。

### RULER：质量损失随输入长度变化

RULER 覆盖 16K、32K、64K、128K 输入长度，使用上述主平台与默认检索预算。平均分取四种长度结果的均值，差值单位为百分点。（表 2、表 7，PDF 第 8、15 页）

| 模型 | full attention 平均分（%） | RetrievalAttention 平均分（%） | 平均差（百分点） | full attention 的 128K 分数（%） | RetrievalAttention 的 128K 分数（%） |
|---|---:|---:|---:|---:|---:|
| Llama-3-8B | 83.91 | 81.70 | -2.21 | 78.74 | 74.70 |
| Yi-9B | 70.90 | 70.38 | -0.52 | 60.51 | 59.15 |
| Yi-6B | 61.22 | 58.90 | -2.32 | 55.77 | 51.44 |

最长输入上的质量损失比均值更明显。Llama-3-8B 在 128K 上下降 4.04 个百分点，四种长度的平均下降为 2.21 个百分点。论文所说的“near full attention accuracy”仍伴随可测的质量损失。

### 解码延迟：收益主要来自减少检索扫描

表 9 使用 Llama-3-8B 和 RTX4090 + i9-10900X，附录 A.6 指明上下文为 128K。正文的上下文长度扫描实验另有 100-token 用户输入。耗时单位为秒/生成 token，包含完整解码步，离线建索引和请求 prefill 另计。表中未注明生成 token 总数和 batch。（§4.3、表 9，PDF 第 8–9、17 页）

| 方法 | 检索 | CPU 注意力 | 其余开销 | 完整解码步 |
|---|---:|---:|---:|---:|
| Flat 精确 KNN | 0.791 | 0.016 | 0.041 | 0.848 |
| IVF | 0.243 | 0.017 | 0.040 | 0.300 |
| RetrievalAttention | 0.051 | 0.016 | 0.040 | 0.107 |

按完整解码步计算，RetrievalAttention 相对 Flat、IVF 分别加速约 7.93×、2.80×。论文另报的约 94%、79% 降幅对应检索分项。这些数字的比较对象和计时范围不同，均不能直接作为相对 full attention 的完整请求加速。

表 10 将同一配置的耗时进一步拆为检索、CPU 注意力、GPU 注意力、PCIe、结果合并和其他层。PCIe 只占 0.002 秒/步，主要开销已转到 CPU 检索。CPU 本地计算减少了传输，但分项计时还不足以说明两端计算能完全重叠。（PDF 第 17 页）

图 7 固定 128K 前缀，将新用户输入从 10 增至 2K tokens：在线 prefill 变慢，decode 变化较小。这项实验沿用了准备好的前缀和索引，无法据此判断首次长文档预处理的速度。图 8 的 batch 只测到 4，图 12 则显示 CPU 核数会影响解码延迟；高并发下的吞吐扩展仍需测试。（PDF 第 9、17 页）

|---|---:|
| Llama-3-8B | 788.2 |

附录 C 给出精确 Q–K 近邻构建的复杂度为 $O(n^2d)$，投影和补边另有开销。附录 A.11 的表 13 显示，缩短构建时间后，达到同一召回目标需要扫描更多 token：离线省下的时间，可能转为后续每次查询的成本。（PDF 第 19–20 页）

是否值得建索引，要看同一前缀能复用多少次。若复用 $R$ 次，可以用下面的时间回本条件作粗略判断：

$$
R\bigl(T_{\mathrm{baseline,online}}-T_{\mathrm{RA,online}}\bigr) > T_{\mathrm{extra,index}}.
$$

这是按总耗时作的推算，两边要采用相同的模型、上下文、输出长度、硬件和质量要求；额外构建成本还应扣除基线已有的前缀预处理成本。上面的建索引时间对应 100K，单步延迟对应 128K，两者不足以算出可靠的回本次数。

## 理解、局限与疑问

### 对设计的理解

1. 索引要适配 Q→K 最大内积检索。单看 K–K 近邻图的质量，还不足以判断它在注意力中的搜索效率。这是后续 KV 存储系统可以借鉴的设计思路。
2. CPU 保存大量 KV，也承担检索和局部注意力；GPU 负责模型主体和常驻集合。这样的分工同时影响 KV 容量和每步 PCIe 传输量。
3. 完整 KV 的存储量、搜索候选的扫描量、最终参与注意力的动态 KV 数，需要分别计算。扫描比例无法直接换算成显存或主存压缩比。
4. 索引召回与任务质量需要分别评估。高 recall@100 有助于降低检索误差，但 KV Retrieval 仍受益于 top-2000 的更大预算。

### 尚未解决的问题

- 前缀固定且可以复用，是当前方案的前提。按 KV 复用的条件推断，模型权重、位置编码配置或前缀内容发生变化后，需要重新确认缓存和索引是否有效。本文尚未展示通用的低成本增量更新方案。
- 去掉索引中的 Q 节点后，CPU 仍需保存完整 KV、图边和索引元数据。**论文没有完整报告 CPU 峰值内存、索引字节/token、构建临时内存和运行时显存分解，实际内存占用还需要测量。**
- 附录 B.2 明确将短用户输入 KV 放到 GPU，算法 1 却没有完整展开生成 KV 的持续插入、窗口滚动、迁移和重建策略。长输出、长会话的内存与检索开销因此还不清楚，需要结合对应实现核查。
- 附录 C 依赖启发式索引和实证评估。搜索接近 $O(\log n)$ 的描述以 OOD 已缓解等条件为前提，未给出最坏情况保证；索引召回、稀疏注意力误差与任务质量之间也缺少通用的严格保证。
- §2.1 先讨论无 KV cache 时每步重算的二次复杂度，并以表 1 举例，后面才转向带 KV cache 的线性注意力。标准带缓存、单 query 的 decode 对历史 KV 的注意力复杂度是 $O(nd)$，阅读前半段时要留意这一条件。（PDF 第 3 页）


### 与相关路线的联系

- StreamingLLM/SnapKV 保留固定窗口或预先选定的重要 token；RetrievalAttention 按当前 Q 动态检索 CPU 中的完整历史 KV。
- Quest/InfLLM 通过页或块的代表信息估计相关性，RetrievalAttention 则用适配 Q/K 分布差异的向量索引寻找 key。本文的对照结果取决于具体预算和配置，尚不能涵盖这些方法的全部使用场景。
- [MagicPIG](../magicpig/meta.yaml) 在本文基线中通过 LSH 哈希碰撞查找相关 key。这里比较的是特定参数下的结果，未完整复核 MagicPIG 自身的采样估计机制和全部实现；RetrievalAttention 使用的是注意力感知图索引。
- KV 量化减少每个 KV 的存储与带宽成本，RetrievalAttention 减少每步访问量并改变数据和计算的位置。作者认为二者正交，但未验证组合后的检索排序、质量和速度，组合收益需要另测。（§5，PDF 第 10 页）
- 正式版将 RetroInfer 列为后续相关工作，当前 `microsoft/RetrievalAttention` 仓库的 README 也介绍 RetroInfer。该仓库的 wave index、wave buffer 等机制属于另一项工作，与本文实现需要分开核查。（参考文献 [48]，PDF 第 14 页；[仓库页面](https://github.com/microsoft/RetrievalAttention/)）

### 对端侧部署的判断

我的判断是，这套方案更适合独显显存有限、CPU 主存充足，且会反复使用同一知识前缀的桌面或工作站应用。RTX4090 实验支持了这种异构配置的可行性；手机、Jetson 和 NPU 上的收益尚无对应实测。

统一内存设备的瓶颈可能不同：CPU/GPU 未必受同样的 PCIe 传输限制，却可能争用共享带宽和功耗预算。图遍历的随机访问和 CPU 算力也可能限制性能。这些是部署层面的推测，需要在目标设备上验证。

实际采用前，我会先确认前缀的复用次数，再测包含构建、加载和 prefill 的冷启动耗时。质量与检索预算的关系、长输出时的 KV 管理、CPU 峰值内存和能耗也需要补测。最终比较应落在同等质量、同等资源限制下的端到端请求延迟。本笔记只讨论论文结果，尚无本人复现实验。
